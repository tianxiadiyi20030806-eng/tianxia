# 零依赖实现一个中文 RAG 系统：我踩过的 6 个坑

> 全程只用 Python 标准库，没有 LangChain、没有向量数据库、没有 pip install。
> 项目地址：[gitee.com/tianxiawo/tianxia](https://gitee.com/tianxiawo/tianxia)

## 背景

准备「网络系统管理」赛项时，手头有 4 份资料（赛题样题 PDF、模块试题 docx、
技术文档），共约 4 万字。想查「B 模块的 DHCP 中继怎么配」，需要在 PDF 和
Word 里反复翻找，耗时数分钟。

于是我做了个知识库问答系统：**输入问题，从资料中检索相关段落，
由大模型基于资料回答，并标注来源。**

约束条件：**只允许用 Python 标准库**。原因很简单——我的环境装不了 pip。

后来发现这个约束反而成了优势：**为了不用库，我必须搞懂每个环节的原理**，
也因此踩到了很多"调库时永远不会遇到"的坑。

下面是其中 6 个。

---

## 整体架构

```
原始资料 (PDF / Word)
      ↓  ① 文本提取
   纯文本
      ↓  ② 清洗修复
   规整文本
      ↓  ③ 切块（标题层级 + 面包屑）
  131 个知识块
      ↓  ④ 中文分词 + TF-IDF 建索引
    索引
      ↓  ⑤ 检索 Top-3        ← 用户提问
  相关段落
      ↓  ⑥ 拼提示词 + 调用 LLM
  带来源的回答
```

## 坑 1：PDF 抽取出来的标题，被"吞"进了上一段

用 `pdftotext -layout` 提取文本后，我发现章节标题大量错位：

```
修复前：
注：本题目中没特别说明的密码皆为：ChinaSkills23。1．DCserver 系统基础环境配置

修复后：
注：本题目中没特别说明的密码皆为：ChinaSkills23。
1．DCserver 系统基础环境配置
```

**统计下来：PDF 里「N．」格式的二级标题，被吞了 12 处，干净独立成行的只有 5 个**
——约 70% 的二级标题都错位了。

**如果不管它，按标题切块时 70% 的边界会全部错位。**

### 解法

写正则重新断行。但这里有**陷阱**：语料里全是 IP 地址，正则是
`([。；])\s*([0-9]+[．、.](?=[^\d]))`——**多写了一个负向断言 `(?=[^\d])`**。

为什么？看这个案例：

```
172.16.100.221；8.8.8.8；5．为 ChinaSkills.cn 域配置安全策略
                 ↑         ↑
             这个是 IP    这个才是标题
```

`；8.` 后面跟的是数字 `8`，所以被排除；`；5．` 后面跟的是中文，才被判为标题。

**没有这个断言，82 个 IP 地址会被切得七零八落。**

## 坑 2：一个看不见的字符，让整个逻辑失效

修好标题断行后，我加了个"把被换行截断的行接回去"的逻辑，结果**面包屑全乱了**：

```
模块B：服务部署目  录 › Linux项目任务描述你作为一个Linux的技术工程师，被指派去构建...
```

排查了很久才发现，问题出在一个**肉眼不可见的字符**上：

```
第 276 行: 缩进=2
        原始字符码: 0xc 0x20 0x4e00 0x3001
                    ↑     ↑
                换页符   空格
```

`pdftotext` 在**每页边界插入换页符 `\f`（0x0C）**。它被 Python 当作空白字符，
于是"1 个空格的缩进"被算成了 2 个，触发了本不该触发的拼接条件。

### 解法

```python
# 第一步就把换页符处理掉
text = text.replace("\f", "\n")
```

### 教训

**遇到"逻辑明明对但结果不对"时，去看数据的原始字节。**
`hexdump` 比读十遍代码有用。

## 坑 3：目录污染检索

切块前我漏了一件事：**目录（TOC）里有所有标题文字。**

后果是：**任何查询都会命中目录块**——因为目录里什么标题都有。

```
目录片段：
模块 A-网络构建 .................................... 2
 一、基础配置 ...................................... 3
 二、有线网络配置 .................................. 3
```

检索"VLAN 修剪"，目录块因为含"有线网络配置"而得分，挤占了真正的内容块。

### 解法

识别并整体剔除目录区。两种目录格式都要处理：

| 类型 | 特征 | 正则 |
|---|---|---|
| PDF | 标题 + 点线 + 页码 | `\.{4,}\s*[0-9]+\s*$` |
| docx | 标题 + 页码直接相连 | `^.{1,40}[0-9]\s*$` |

## 坑 4：中文分词——IP 地址被切成了 4 段

中文没有空格，检索前必须分词。检索排序（坑 5）算不对，根源也在这里。

我用的方案是**二元切分（bigram）**：把连续的中文每相邻两字组成一个词。

```
"中继怎么配"  →  中继 | 继怎 | 怎么 | 么配
                 ✅     噪音    ✅    噪音
```

中间那两个"噪音词"无害——它们在任何块里都不会出现，得分自然为 0。

### 但有个陷阱：ASCII 部分不能被切开

```
tokenize("172.16.100.221")  →  ['172.16.100.221']   ← 必须是一个词
tokenize("配置DHCP服务")     →  ['配置', 'DHCP', '服务']
```

**如果按字符切，`172.16.100.221` 会变成 `172`/`16`/`100`/`221` 四段，
彻底失去意义。**

所以分词器要先按"字符类型"分组（中文 / 字母数字点 / 其他），再对中文段做二元切分。
核心判断：

```python
def char_type(ch):
    if '\u4e00' <= ch <= '\u9fff':
        return "cn"
    if ch.isascii() and (ch.isalnum() or ch == "."):
        return "ascii"      # 注意：小数点也要算进来，否则 IP 会被切开
    return "other"
```

## 坑 5：常见词把检索分数"灌水"了

最初的打分逻辑很朴素：**问题里的词，在块里命中一个就加 1 分。**

结果出现了明显的误判：

```
问题："怎么配置WSUS更新服务"
分词：['怎么', '么配', '配置', 'WSUS', '更新', '新服', '服务']
                      ↑ 出现于 74 个块      ↑ 出现于 2 个块
                       毫无区分度              极强区分度
```

**但按"命中一个加 1 分"，`配置` 和 `WSUS` 权重完全一样。**

一个不含 WSUS 的块，因为碰巧有一堆常见词，分数就能追平正确答案。

### 解法：IDF 加权

**一个词出现的块越少，它越有价值**——因为命中它能排除掉更多块。

```
权重 = 总块数 ÷ 出现该词的块数

WSUS  → 131 / 2  = 65.5    ← 稀有，权重高
配置  → 131 / 74 =  1.8    ← 常见，权重低
```

实测权重表：

| 词 | 出现块数 | 权重 |
|---|---|---|
| WSUS | 2 | 65.5 |
| 中继 | 2 | 65.5 |
| VLAN | 6 | 21.8 |
| 配置 | 74 | 1.8 |
| 服务 | 73 | 1.8 |

**`WSUS` 的权重是 `配置` 的 36 倍。**

改完之后，Top-1 与次优结果的分差从 **2:1 拉开到 7:1**。

## 坑 6：我以为自己的检索很准，直到我做了评测

写完检索后我"感觉"效果不错。但**"感觉"不是数据**，而且面试官一定会问
"你怎么知道检索准不准"。

于是我构建了一个 **28 题的人工标注测试集**，分两组：

| 组别 | 说明 | Top-1 | Top-3 |
|---|---|---|---|
| A 组：直接提问 | 使用原文术语（"DHCP中继怎么配"） | **100%** | **100%** |
| B 组：改写提问 | 用同义表达（"怎么让客户端自动获取IP"） | 75% | 75% |

**A 组 100% 看着很漂亮，但 B 组的两个失败案例暴露了真问题：**

| 失败的问题 | 期望答案 | 根因 |
|---|---|---|
| 怎么限制员工上班时间**玩游戏** | P2P 应用阻断 | 语料原文是"P2P 应用软件"，**没有"游戏"一词** |
| 怎么让**外网**访问**内网**服务 | NAT 配置 | 语料原文是"内部客户端访问**互联网**"，**用词完全不同** |

**两个失败案例根因相同：关键词检索只能匹配字面，对同义表达完全无能。**

这是关键词检索的**固有局限**，调参解决不了——**必须引入向量检索（Embedding）
做混合检索**。

### 教训

**"我的系统很准"和"我知道我的系统哪里不准、为什么不准"，
后者才是工程能力。** 一个诚实的 75% 比一个可疑的 100% 有价值。

## 加分项：零依赖实现 MCP Server

最后一步，我把检索能力封装成了**标准 MCP Server**，可以被 Claude Desktop /
Cursor / Cline 等 AI 应用直接调用。

大多数教程会让你 `pip install mcp`——但**协议本身很简单**：

```
传输层：stdio —— 从标准输入读消息，往标准输出写消息
消息格式：JSON-RPC 2.0
核心方法只有 3 个：
    initialize    握手
    tools/list    列出工具
    tools/call    调用工具
```

**用 `sys.stdin` / `sys.stdout` / `json` 就能实现，约 150 行。**

关键的几个设计点：

```python
def send(msg):
    """往 stdout 写一条 JSON-RPC 消息（每条一行，这是 stdio 传输的约定）"""
    sys.stdout.write(json.dumps(msg, ensure_ascii=False) + "\n")
    sys.stdout.flush()          # ← 必须 flush，否则消息会卡在缓冲区里
```

```python
# 工具声明用 inputSchema（注意不是 OpenAI Function Calling 的 parameters）
{
    "name": "search_knowledge_base",
    "description": "在知识库中检索...",
    "inputSchema": {"type": "object", "properties": {...}, "required": ["query"]},
}

# 工具结果放在 content 数组里
{"content": [{"type": "text", "text": "检索结果..."}]}
```

因为 MCP Server 由客户端通过 stdio 启动，手动运行会看到卡住的终端，
所以还需要写一个测试客户端来验证：

```
✅ initialize 握手成功，服务器：knowledge-base-server v1.0.0
✅ 服务器提供 1 个工具：search_knowledge_base
✅ tools/call 返回检索结果（相关度 84.2，来源块 #20）
```

## 总结

这个项目让我最深的体会是：

> **不用框架，逼你搞懂原理；搞懂原理，才知道框架在替你做什么。**

6 个坑里有 4 个（PDF 标题错位、换页符、目录污染、IP 被切碎）**用 LangChain
根本遇不到**——因为库已经替你处理了。但遇到库处理不了的场景时，
**知道原理的人才有办法。**

另外三点经验：

1. **验证要贯穿始终**——每次修复后都要验证，因为一个改动可能引入新 bug
   （我在坑 2 就干过）
2. **验证脚本自己也可能有 bug**——我的测试关键词写成了"Windows 防火墙"（带空格），
   而语料是"Windows防火墙"，差点误判成检索失败
3. **评测比优化重要**——不知道基线在哪，优化就是盲目的
